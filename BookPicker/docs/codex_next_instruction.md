今回の設計方針は以下です。

詳細ビューは、読書中に頻繁に行う操作を素早く実行する場所とします。

詳細ビューでは CurrentPage と読了状態を変更可能にします。

編集ビューは、本の情報全体を変更する場所とします。

編集ビューでは Title、CurrentPage、TotalPages、Genre、InterestLevel に加えて、読了状態も変更可能にします。

ただし、内部のAPI責務は維持してください。

CurrentPageだけを詳細ビューから更新する場合は、既存の progress API を使用してください。

本の一般情報を編集する場合は、既存の一般編集APIを使用してください。

読了状態を変更する場合は、既存の completion API を使用してください。

一般編集APIへIsCompletedを追加しないでください。

バックエンドのAPI仕様やドメイン設計は変更しないでください。

編集保存時について。

一般編集項目は既存の

PUT /api/books/{id}

を使用してください。

読了状態は既存の

PUT /api/books/{id}/completion

を使用してください。


一般編集APIへ送る項目は現在のAPI仕様どおりとしてください。

Title。

Genre。

TotalPages。

CurrentPage。

InterestLevel。

既存CoverImagePath。

ReadingStatus、LastReadAt、IsCompletedは一般編集リクエストへ追加しないでください。


編集保存時に一般情報と読了状態の両方が変更されている場合は、まず一般編集APIを実行してください。

その一般編集が成功した後で、編集フォーム上で選択された最終的な読了状態をcompletion APIへ反映してください。

この順番にする理由は、TotalPagesやCurrentPageの最終状態を先にBookへ反映してから、読了操作を適用するためです。


例えば編集画面で以下の状態へ変更した場合です。

CurrentPageを100へ変更。

TotalPagesを180へ変更。

読了状態を読了済みへ変更。

まず一般編集APIで100 / 180を保存してください。

その後completion APIで読了済みを指定してください。

結果としてバックエンドの読了ルールによりCurrentPageは180へ変更されます。


逆に読了解除を選択した場合も、一般編集API成功後にcompletion APIでisCompletedをfalseとして反映してください。

バックエンド側の読了解除ルールに従ってください。


編集保存中は保存ボタンを一時的にdisabledにし、二重送信を防いでください。

一般編集APIが失敗した場合はcompletion APIを実行しないでください。

一般編集が成功し、completion APIが失敗した場合は、ユーザーへ部分的な保存が発生したことを隠さないでください。

その場合は最新状態をGET APIから再取得し、実際に保存された状態を画面へ反映した上で、読了状態の変更に失敗したことをエラー表示してください。


この二段階更新については、現在のバックエンドAPI構成上必要な処理として、読みやすい関数構造にしてください。
